How ArgoCD Works: Root Application, Projects & Applications

Rather than deploying workloads imperatively, GitOps uses declarative configuration as the single source of truth. Below is an overview of how the Root Application, AppProjects, and Child Applications operate together.

1. The App of Apps Pattern

Instead of a single monolithic manifest managing every component, this repository uses the App of Apps pattern. A parent root application watches the Git repository and provisions independent child Application resources for each workload.

Root Application
root-application.yaml (monitors apps/)
Child Application
apps/demo-app.yaml (monitors components/demo-app)
Governance Boundary
AppProject (default project)
Workload Target
demo-app namespace

2. The Root Application (Bootstrap Entrypoint)

The root application is the single registration step for the entire repository. Once applied to Kubernetes, it monitors the apps/ directory in Git and automatically creates each service's Application custom resource.

Declarative Root Application manifest (root-application.yaml):

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root-application
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/vmalani27/gitops-repo-apps.git
    targetRevision: main
    path: apps
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

3. AppProjects (Tenancy and Access Control)

An AppProject defines a logical security boundary around applications. While this local setup uses the default project, production environments use projects to isolate teams, enforce policies, and restrict permissions.

Source Repositories
Whitelist approved Git repositories and branches.
Cluster Destinations
Restrict target clusters and target namespaces.
Cluster Resource Restrictions
Block applications from creating ClusterRoles or CRDs.
Namespace Resource Restrictions
Whitelist standard workloads (Deployments, Services, Ingress).

4. Child Applications (Individual Workloads)

Each workload inside components/ has a dedicated Application manifest in apps/. This gives every service its own health tracking, sync status, and rollback history.

Demo application manifest (apps/demo-app.yaml):

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: demo-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/vmalani27/gitops-repo-apps.git
    targetRevision: main
    path: components/demo-app
  destination:
    server: https://kubernetes.default.svc
    namespace: demo-app
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
automated.prune: true
Deletes cluster resources when deleted from Git.
automated.selfHeal: true
Detects manual cluster drift and restores Git state.
CreateNamespace=true
Automatically provisions the destination namespace.
Failure Isolation
Issues in one service do not affect other applications.

5. Inspect and Test the Deployment

You can inspect and test GitOps operations directly from your terminal:

List all ArgoCD applications and their sync status.

kubectl get applications -n argocd

Inspect the detailed status and live sync tree of this application.

kubectl describe application demo-app -n argocd

Test self-healing: delete this pod and verify that ArgoCD recreates it automatically.

kubectl delete pod -n demo-app -l app=demo-app

View the graphical deployment topology in the ArgoCD web console.
